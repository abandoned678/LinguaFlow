# 输入法任务协调

当前对话持有需求、依赖和最终验收结论。按[项目规则](../../../AGENTS.md)识别用户意图。仅在长期取舍会影响后续设计时使用[架构决策记录](../../../docs/ARCHITECTURE_DECISIONS.md)。

## 从需求到派工

从用户的话、已有 spec 或 plan 提取可观察行为，保留“先 review”“通过再提交”等条件。把待验证的假设与已确定的产品选择分别记录。文档之间冲突时先确定本次请求依据，仍有歧义且会改变行为时交回用户决定。讨论或规划的产物可以是对话中的表格。

给每个受派者发一份可独立理解的任务简报：

| 交接项 | 内容 |
| --- | --- |
| 目标 | 用户操作、预期结果、原需求出处 |
| 写入范围 | 文件或模块、已有未提交改动、共享文件的唯一写入者 |
| 依赖 | 上游接口、资源、前置产物，哪些工作可以先进行 |
| 验收条件 | 正常路径、边界或失败结果，以及合适的验证层 |
| 回报 | 改动路径、执行的命令或运行 ID、实际结果、待验事项 |

例如“每页候选可选 5～10 项”可以交给一个实现者打通设置到候选上屏。让验收者独立从需求推导默认 5、选 10 后重启仍为 10、第 10 项可上屏等检查。按[体验规格 A2、D1](../../../docs/DAILY_INPUT_EXPERIENCE_SPEC.md)分别记录键盘和鼠标选末项的结果。D1 中用 0 选第十项仍待评审时，点击通过只关闭鼠标验收项。

## 调度与集成

- 按根规则选择本次需要的角色。文档任务可派一个实现者，由主 Agent 用真实命令、链接或使用场景复核。涉及宿主写入等高风险行为时，可在开发期间派验收者从原始需求设计用例，集成后复测同一构建。
- 文件和接口重叠时指定一个写入者，其余角色先读代码、设计测试或等待接口。共享工作区默认直接交接 diff；需要不同基线、隔离冲突改动或前后对照时再用 worktree，记录分支和基线，由协调者集成并复测最终组合。
- 构建共用同一 SwiftPM scratch 目录时串行，独立目录才并发。安装输入源、选择 TIS、前台取焦和发键共享同一登录桌面，在一个时间段里只派一个执行者。已有授权按会话沿用。
- 工具支持命名角色时加载对应角色配置。接口只接受任务描述时，简报中附角色文件路径与操作边界。给通用 reviewer 写明“只读检查，不改文件”，交付时注明“通用子代理按只读简报评审”。仅在确认运行时应用了只读沙箱时才报告该权限保证。无法委派时由主 Agent 明示自己完成的检查及独立验收缺口。
- 子代理回传越界需求、未确定的产品行为或实际阻塞给协调者，由协调者调整依赖和分工。无须让子代理再次启动一层协调者。

## 复核与关闭

实现者交回改动后，由本次负责复核的人检查实际 diff 和验收条件。已安排独立评审时，由 reviewer 核对受影响的调用链。发现问题时主 Agent 把位置、触发条件和预期结果派回实现者，随后组织原失败用例复测。在任何需要独立性的环节保留实际执行者身份。

协调者逐条对照原需求与现有产物，抽查文件、命令结果或报告中的构建号。对每条验收标明通过、失败、受阻或未执行；写明来源是代码检查、受控回归、专用宿主、指定真实宿主自动化或实体键盘。保留宿主、构建及限制，例如“TextEdit 自动化通过；Codex 实体键盘通过；Codex 自动化在焦点识别处受阻”。若用户要求先验收再提交，保留改动供 review。获得提交授权后核对实际 diff 和未跟踪文件；分别按实际发生的操作报告本地提交、合并或推送。
